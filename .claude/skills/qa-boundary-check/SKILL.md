# 연결부 정합성 검증

각 구성 요소의 단위 테스트가 통과해도 연결 지점에서 계약이 어긋날 수 있다. 이 체크리스트는 **생산자와 소비자 코드를 함께 열어 비교**하는 것을 원칙으로 한다.

## 1. 기계 검사 (항상 먼저)

```bash
pnpm -r typecheck
pnpm -r test
pnpm --filter web build      # 화면이 포함된 경우
pnpm --filter api prisma validate
```

실패하면 원인 출력과 함께 기록하고 나머지 검사를 계속한다.

## 2. 대상별 체크리스트

### API 모듈
- [ ] 각 엔드포인트가 계약 문서의 메서드·경로·인증과 일치한다.
- [ ] 응답이 `serialize(Response스키마, …)`를 거친다. 거치지 않는 반환문을 `grep`으로 찾는다.
- [ ] 목록 응답이 `{ items, next_cursor }` 형태다.
- [ ] 오류가 `{ code, message }`이고 `code`가 shared `ErrorCode`에 있다.
- [ ] 권한: 비로그인, 일반 멤버, 방장, 운영진 각각으로 접근했을 때 결과가 명세와 같다.
- [ ] 상태 갱신 코드 전수 검색(`status:` 갱신) → shared 전이 맵에 없는 전이가 없고, 맵의 전이 중 구현되지 않은 것이 없다.

### 화면
- [ ] 화면의 각 훅 → 호출 경로 → API 컨트롤러 경로가 실제로 존재한다.
- [ ] 훅이 응답을 shared 스키마로 `parse`한다(제네릭 단언만 있는 곳을 찾는다).
- [ ] 모든 `href`, `router.push`, `redirect` 값이 `app/` 라우트 구조와 일치한다.
- [ ] skill `nextjs-dashboard-ui` 4절의 필수 상태가 모두 처리된다.

### 교차 대조 (슬라이스 단위)
- [ ] 계약의 엔드포인트 목록 ↔ 컨트롤러 목록 ↔ 웹 훅 목록 일대일 표. 웹에서 안 쓰는 것은 봇/관리용인지 표시.
- [ ] snake_case 필드가 웹까지 그대로 오는지(중간에 camelCase로 바뀌는 곳이 없는지).

### 도메인 무결성 (내전·레이팅 관련 슬라이스)
- [ ] 결과 승인 두 번 호출 시 레이팅이 한 번만 반영된다(테스트 존재 확인 또는 직접 실행).
- [ ] 마지막 자리 동시 참가 테스트가 있다.
- [ ] 백엔드가 계산식을 재구현하지 않고 `packages/core`를 호출한다.
- [ ] `core` 테스트에 `formulas.md`의 문서 예시값이 들어 있다.

### 외부 연동
- [ ] 코드·fixture·로그에 API 키가 없다(`grep -ri "RGAPI-"` 등).
- [ ] 429 처리 테스트가 있고, 401/403은 재시도하지 않는다.
- [ ] 외부 호출이 브라우저 코드(`apps/web`)에 없다.

### 명세 대조
- [ ] 개발 문서 2장의 이번 슬라이스 P0 기능이 모두 구현됐다. 빠진 것은 "누락"으로 기록.
- [ ] 스키마에 `discord_id`, `activity_logs.idempotency_key`(unique), `api_keys.key_hash`가 있다.

## 3. 보고서 형식 (`_workspace/03_qa-verifier_{target}.md`)

```markdown
# QA: {target}  — 판정: pass | fail | blocked
## 실행한 명령과 결과
## 결함
| # | 심각도 | 위치(파일:줄) | 기대 | 실제 | 재현 |
## 교차 대조 표 (해당 시)
## 이전 결함 재확인 (재검증 시)
```

판정 기준: `blocker` 또는 `major`가 하나라도 있으면 `fail`. 환경 문제로 검사 불가면 `blocked`.
